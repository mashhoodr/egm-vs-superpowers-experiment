Three ways to build the same tool

I gave Google's Elephant-Goldfish Model, Superpowers and a plain agent the same brief. All three passed the tests. The differences were in what the tests didn't check, and in the bill.

The setup

We keep wrapping more process around coding agents - brainstorms, written plans, reviewer swarms - and the return on that overhead is still mostly anecdotal. I wanted a number, so I ran EGM and Superpowers against a plain agent with no plugin, in parallel in Claude Code, on the same model, building the same thing: txmerge, a small Python CLI that merges overlapping bank CSV exports into one ledger. It has to remove duplicates without losing real transactions, link transfers between my own accounts and categorise the rest with rules.

The brief was deliberately loose. A scripted stakeholder agent held 13 hidden policies - two identical coffees on the same day in one export are both real, a transfer must land within 3 days - and only answered what it was asked. I scored the arms on 18 hidden acceptance tests, a 10-case robustness probe, blind code and design reviews, and token spend rebuilt from every agent's transcript.

  • EGM has a deep-context "elephant" agent draft a design spec, then sends it to zero-context "goldfish" reviewers before any code is written.
  • Superpowers goes from brainstorm to written plan to subagent-driven development, with test-driven development and review on each task.
  • Baseline is the agent on its own.

Everyone passed the tests

All three arms scored 18/18. The baseline asked 14 questions in a single batch and got every policy, which tells me the brief was too easy to separate the workflows on rule-following.

The difference showed up in the brief's own first requirement: never lose a real transaction. I fed each tool a CSV where one row had an unclosed quote and two valid rows followed it.

Superpowers' 6 per-task reviews had all passed first time; the one bug that mattered came from its single review of the whole branch at the end. In the blind code review, EGM and Superpowers tied on 16/20, with EGM ahead on correctness, and the baseline came third on 11/20. EGM's design scored 20/25 against Superpowers' 16/25, and it uncovered 11 of the 13 policies, against 10 for Superpowers and 9 for the baseline. But the spec ran to about 580 lines for a tool of about 450.

The orchestrator is the bill

The baseline processed 0.85M tokens in 5 minutes, Superpowers 17.6M in 28 minutes and EGM 47.5M in 71 minutes. Weighted by what each kind of token costs, that is 1×, 15× and 36×.

The subagents were not the expensive part. 93% of EGM's tokens and 74% of Superpowers' went on the orchestrator - the main agent that dispatches all the others - re-reading its own growing context on every call. EGM's 39 reviewer runs cost about 2M tokens, but pasting their 46 reports back into the orchestrator pushed its context to 458k. Neither EGM review loop converged either; both stopped at the 5-round cap, with the style reviewer finding fresh wording issues every round.

It hasn't been without adventure. The subagent_tokens figure Claude Code reports turned out to be the final context size, not total spend, so my first report understated cost by 7 to 21 times. I rebuilt every number from the transcripts.

Same workflow, opposite answer

I then reran EGM with its synthesizer agent, which keeps reviewer reports out of the orchestrator. Tokens fell 29%, from 47.5M to 33.6M, but weighted cost rose 21%, because the longer waits let the prompt cache expire and the orchestrator rewrote its ~260k context 6 times.

And this run silently lost the rows on the unclosed quote that run 1 had refused. Same workflow, same brief, opposite behaviour. Run-to-run variance was as large as the gap between workflows, so one run per arm proves less than I would like.

What I'd take from it

  • Process bought robustness, not rule-following. Both plugins caught a data-loss bug the plain agent shipped.
  • The orchestrator's context is the bill. Multi-agent workflows should hand reports over on disk and start a fresh context for each phase.
  • One run is an anecdote. Next time I'll run three per arm.

The caveats are real: one task, one model, and a scripted stakeholder instead of a human at the gates. But the cheapest likely win is already visible - a plain agent plus one whole-branch review at the end - and that is the experiment I want to run next. If you have tried something similar, I'd love to compare notes.
